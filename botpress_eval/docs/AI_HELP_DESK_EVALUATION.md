# AI Help Desk Evaluation

Hallucination, fallback, escalation, response latency, real-time performance, availability and reliability

PUP Taguig website and Botpress AI Help Desk | Revised 12 October 2026 | Asia/Singapore

## 1. Study design and evaluated population

The implemented evaluator assesses previously recorded Botpress replies against evidence extracted from local institutional PDFs. It does not submit a new test question to the chatbot, simulate production traffic, or continuously monitor service uptime. Its answer-quality judgments are generated by a local Ollama model and checked by Python for valid numeric/boolean output.

The current saved report contains 100 answered text turns from 16 conversations. First-reply timestamps span 15 September to 6 October 2026 in Asia/Singapore. Latencies were backfilled from the original Botpress logs on 12 October 2026. These are historical observations, not a new live load-test run.

The collector visits up to 100 recent conversations and selects up to 100 eligible turns. A case consists of one incoming text question and assembled outgoing text before the next incoming turn. Recognized feedback prompts, cannot-answer replies and usage-limit notices are excluded before selection. Unanswered questions do not become evaluated pairs. This creates selection bias and limits generalization, particularly for fallback, availability and unsuccessful requests.

## 2. Evidence and evaluator configuration

The local documents consist of six PDFs with 28 source pages: Academic Programs, Campus Information, Enrollment and Admission, Frequently Asked Questions, Student Services, and Systems and Quick Links. The local evaluator does not fetch the production Botpress knowledge base for current scoring.

PDF text is extracted with pypdf and cached by content hash. BM25-style lexical retrieval ranks overlapping chunks using question terms plus answer terms. The judge receives selected evidence within the default 2,400-character budget, not the complete documents. Retrieval can miss synonyms, cross-language matches or relevant facts, and answer-dependent retrieval can affect judgments.

The saved run identifies phi3:mini as the evaluator model and 7.0 as its pass threshold. Defaults include temperature 0, a 4,096-token context setting, a 192-token output cap, one generation attempt, a 90-second request timeout and a two-second pause between cases. These evaluator settings do not identify the production chatbot's LLM or response timeout.

The judge returns three scores from 0 to 10: relevancy, accuracy and faithfulness; it also estimates answerability and refusal. Python validates required values and flags malformed or timed-out output as errors. Valid JSON and high scores do not establish independent factual verification.

All three quality scores must meet the threshold, with an appropriate answer/refusal, for an overall quality pass. The current failed case, index 82, scored 1/10 for all three metrics and was classified as a substantive answer to an answerable question. Its low scores require evidence review; they do not automatically establish a hallucination.

These answer-delivery counts are not mutually exclusive classification buckets. TP is a correct grounded substantive answer to an answerable question. FN is an answerable question without a correct grounded answer. FP is a substantive reply that is incorrect/ungrounded or given to an unanswerable question. TN is a refusal to an unanswerable question. A wrong substantive answer to an answerable question contributes both FP and FN; the counts can exceed the number of cases.

Precision = TP/(TP+FP). Recall = TP/(TP+FN). F1 = 2TP/(2TP+FP+FN). Errors and legacy rows are excluded from these scored metrics and score averages. Overall pass rate uses all report rows as its denominator, so an evaluation error cannot improve the pass rate. Undefined denominators produce N/A.

## 4. Hallucination assessment

For a proposed manual assessment, a hallucinated factual claim is a statement that contradicts the applicable official source or introduces a factual assertion without support in the reviewed evidence. Missing retrieved evidence should be distinguished from proven contradiction and from facts absent because of incomplete documents.

Faithfulness is the existing evaluator's proxy for evidence support. Its mean is 9.780/10, with one of the 100 scored replies below the 7/10 threshold. Report this as a 1% faithfulness-failure proportion in the selected sample, not as a measured 1% hallucination rate. Accuracy and faithfulness scores are generated by the same AI judge and are not independent human labels.

The CSV field Unsupported Answer means refusal/cannot-help behavior in this implementation. It does not count unsupported factual claims. Its value of zero cannot be used to claim zero hallucinations, zero fallbacks or complete coverage.

A defensible hallucination study would retain the original question/reply and dated source evidence, split each reply into factual claims, assign supported/contradicted/not-established labels, and have institutional reviewers adjudicate disagreements. Report both reply-level rate (replies with at least one confirmed hallucination divided by reviewed substantive replies) and claim-level rate if used. No such human-labeled rate is present in the supplied records.

## 5. Fallback behavior

Fallback means declining to provide an unsupported answer, requesting clarification, or directing the user to a verified source when an appropriate answer cannot be established. A technical failure notice, quota limit and a deliberate safe refusal should be recorded separately.

The code recognizes several English and Filipino refusal phrases and filters many of them during collection. Remaining short refusal phrases can override the judge's refusal flag. Consequently, the current sample's zero scored refusals does not measure fallback frequency or effectiveness in the raw conversation population.

Fallback success should be tested with answerable questions, out-of-scope questions, ambiguous inputs, nonexistent procedures and temporarily unavailable sources. A reviewer should label whether an answer was available and whether the bot's refusal/clarification/routing was appropriate. The suggested rate is appropriate fallbacks divided by all fallback-eligible test cases. Also report false refusals on answerable cases. Both rates are currently unmeasured.

## 6. Escalation and human assistance

The inspected Laravel webhook verifies a shared secret, logs event identifiers and returns a no-content response. It does not create a help desk ticket, assign a staff member, forward a transcript, notify an office, or track case resolution. The separate security-incident notification mechanism concerns administrative security and should not be described as chatbot escalation.

The hosted Botpress workflow may contain additional routing, but no workflow export or handoff records were supplied for this assessment. Advice to contact an office is a referral; it is not proof that a human agent received the request.

An escalation test should record the trigger, user acknowledgement, intended office, actual delivery, staff receipt timestamp and resolution state. Delivery success can be reported as received escalations divided by attempted escalations; staff first-response time should be reported separately from bot response time. Current escalation delivery and resolution results are not measured, and end-to-end human handoff is not established.

## 7. Actual response latency

Latency is calculated as the first outgoing nonempty text message's creation timestamp minus the preceding incoming nonempty text message's creation timestamp in the same conversation. Botpress documents the incoming/outgoing direction and createdAt fields used by this measurement. [Botpress Runtime API concepts](https://botpress.com/docs/api-reference/runtime-api/concepts/).

The backfill matched each saved conversation/message ID, question text and first-reply timestamp against the original logs. All 100 cases had valid measured latencies. Missing, negative and nonfinite values are excluded from summary statistics and reported separately; they are not replaced with zero.

| Response-latency measure | Actual result |
| --- | --- |
| Valid sample size | 100 |
| Missing / invalid cases | 0 |
| Median first-reply response time | 6.550 seconds |
| 95th percentile first-reply response time | 11.439 seconds |
| Replies within 5.000 seconds | 17 of 100, or 17.00% |

For ordered latencies x(1) through x(100), the median is [x(50)+x(51)]/2. The nearest-rank P95 is x(ceil(0.95*n)), which is x(95) for n=100. Summary values are displayed to three decimal places; threshold decisions use unrounded measured values.

This is time to the first logged text reply, which may be an acknowledgement. It does not measure complete multi-message answer time, streaming completion, browser rendering or network delivery. Chronological pairing assumes sequential user turns and cannot establish causal attribution for overlapping requests. Latency results inherit the existing answered-turn selection and do not include unanswered requests or excluded notices.

## 8. Explicit real-time criterion and result

The proposed operational definition for this study is a first logged text reply within 5.000 seconds. The aggregate performance target is P95 <= 5.000 seconds, so at least 95% of valid observations satisfy the threshold. This criterion is a study-defined target introduced for the current analysis; it was not pre-registered before the historical conversations were collected and is not a universal standard or Botpress guarantee.

The observed P95 is 11.439 seconds, exceeding the target, and only 17% of the sample is within five seconds. The current sample therefore does not meet the proposed real-time criterion. Good answer-quality scores do not override this latency result.

Future real-time testing should fix the criterion in advance, include first-load and warm sessions, record unanswered/timeout requests, and specify browser/device/network conditions and concurrent load. Measure user submission to meaningful answer display separately if the intended claim is user-perceived real-time performance. No concurrency, cold-start comparison or browser end-to-end latency test is available in the current evaluator.

## 9. Availability

Availability means that the required service is reachable and able to handle the intended interaction during a defined observation window. A website health check, successful static webchat-page fetch and successful AI answer are different levels of service checks.

The repository includes Laravel's /up health route, a server-health endpoint backed by configured CloudWatch/Lightsail CPU and memory metrics, and an optional Lambda page-fetch example. These implementations provide operational hooks, but no continuous uptime series or verified deployed keep-alive history was supplied. CPU/memory status and one successful HTTP GET do not establish AI service availability.

Availability percentage is currently unmeasured. A proposed assessment would monitor both website reachability and a permitted synthetic bot interaction at a declared cadence throughout a fixed window, recording timestamp, status, timeout and outcome. For regularly spaced probes, report successful probes/total scheduled probes and missing probes separately. Call this probe-based availability; claim time-based uptime only when outage duration is observed sufficiently. Do not exclude downtime or monitoring failures silently.

## 10. Reliability

Reliability means consistent completion of the intended request under defined operating conditions. The observed 99/100 quality-pass result concerns selected answered turns, and the zero evaluator errors concern the local judge run. Neither establishes a 99% production service-success rate or 100% chatbot reliability because failures and unanswered requests were filtered out of this sample.

The evaluator validates model outputs, saves error rows and stops on generation timeout/disconnection to avoid repeated delays. It archives prior reports and caches extracted PDFs. Knowledge synchronization tracks failures and hashes, while optional jobs define retries/backoff. These mechanisms support operation but do not establish measured recovery time, delivery guarantees or successful indexing.

For a service-level reliability study, include every attempted request, classify transport failures, timeouts, safe fallbacks and substantive replies, and define acceptable completion before the run. Repeat representative questions across sessions and declared concurrent loads. Report completion rate, answer consistency, failure categories and recovery time, with separate quality and latency metrics. Backup restore testing is required before claiming recoverability. These production reliability results remain unmeasured.

## 12. Reproduction and records

Run commands from botpress_eval, sequentially. The live quality command reads Botpress logs and calls the configured Ollama judge; it can replace the current report after archiving it. The latency-backfill command reads original logs for current cases without rerunning the judge or changing its saved scores.

```powershell
python -m pytest test_botpress.py -s
python compute_latency.py
python compute_f1.py
```

Use python -m pytest tests -q for offline mocked checks. The latency change was validated with 29 passing tests on 12 October 2026. These are evaluator implementation tests, not production service trials. A previously recorded single-case evaluator duration of 18.6 seconds describes local AI scoring, not chatbot latency; projected full-run duration is not a measured full-run result.

Case records retain question/reply text, IDs, first-reply timestamp, quality scores, source headers, count contributions and Response Latency (seconds). Summaries are in f1_metrics.csv and latency_metrics.csv. Preserve dated PDFs, settings and model details alongside archived CSVs. No CSV conversation text or identifiers are reproduced in this PDF.
